# 学习路径

这份讲每一层在搞懂什么、为什么按这个顺序、学完应该能回答什么问题。
验收标准和当前进度在 [roadmap.md](roadmap.md)，选型理由在 [decisions.md](decisions.md)。

## 为什么从零写

agent 框架（LangChain、LangGraph、Claude Agent SDK、OpenCode）把循环包起来了。
包起来的代价是：出了问题你不知道是模型的错、框架的错、还是自己接法的错。
先自己写一遍，框架里的每个机制就都有了对照物——再去读它们，是在看别人怎么解决
你已经遇到过的问题，而不是在看一堆没有上下文的抽象。

所以顺序是固定的：每一层都依赖前一层里亲手见过的现象。跳层会把后面的东西学成口诀。

## 第 1 层 一次调用

搞懂一次请求里到底有什么。三件事：

- **内容是块，不是字符串。** 一条助手消息里可以同时有思考、正文、工具调用，
  所以消息的 content 是块的列表。四种块的定义在 `domain/message.py`。
- **流是事件，不是整段。** 回答是一个个片段推回来的，结束原因要等流完才知道。
  结束原因有三种：说完了（end_turn）、被长度掐断（max_tokens）、想调工具（tool_use）。
- **API 无状态。** 服务器不记得上一轮，所以历史每次都整段重发。
  这一条是后面所有「贵」和「慢」的根：工具循环每多一圈就多付一次首 token 延迟。

两家协议（Anthropic / OpenAI）形状不同，差别全部收在 `infrastructure/adapter.py`，
其余代码只看见一套类型。先记住这个边界，后面每加一个字段都要问：
这是协议差异，还是我们自己的概念。

## 第 2 层 一个工具 + 手写循环

搞懂 agent 和「聊天」的差别：模型不只是回答，它还会停下来要求你做事，
你做完再告诉它，它再决定继续要还是收尾。

循环就一句话——`stop_reason == tool_use` 就执行工具、把结果追加进历史、再请求，
直到它不再要工具。三个容易误解的点：

- **工具不是注册到服务器的。** 服务器无状态，工具定义（名字、说明、参数 schema）
  每次请求都要重新带上。注册表活在我们自己的进程里。
- **配对靠 id，不靠顺序。** 一次回复里可以有多个工具调用，结果必须按 id 对回去。
- **执行模型给的参数禁止 eval。** calculator 用 ast 白名单求值，
  只放行数字和四则运算。模型提交的任何表达式都是不可信输入。

循环本体在 `application/conversation.py` 的 `turn()`，CLI 和 web 只消费它吐出的事件。

## 第 3 层 多工具、并行、失败

搞懂「一次回复里不止一个动作」和「动作会失败」。

模型可以同时要两个工具，两个都得执行，结果放进**同一条**消息交回——拆成多条
会让模型学乖，以后不再并行。失败也要交回（带 is_error），而不是把异常抛掉：
模型看到错误描述才能换个路子，看不到就只会重试同一个错误。

这一层开始碰「并发」这个词的两个不同方向，别混：
一个会话内部的并行调用，和多个会话之间同时跑，是两回事。

## 第 4 层 上下文管理

搞懂长对话为什么变贵、变慢，以及能做什么。

历史每次整段重发，所以第 N 轮要重新读一遍前 N-1 轮。三个手段，解决的问题不同：

- **缓存**：前缀不变的部分让服务器别重算。缓存是按字节前缀匹配的，
  前缀里任何一个字节变了，后面全部失效。所以稳定的内容（工具定义、系统提示）
  要放在变化的内容（本轮问题）前面。
- **截断**：历史长过窗口时，丢掉最老的部分。
- **压缩**：与其丢，不如把前面的内容总结成一段再带上。

用量和缓存命中率已经记在 trace 里（`cache_hit_ratio`），这一层的效果能直接看到。
注意 input_tokens 只是没走缓存的部分，真正的输入总量要把它和缓存读写相加。

## 第 5 层 MCP

搞懂工具从哪来。前四层的工具都是自己写死在进程里的；MCP 让工具来自外部进程，
对方说它有哪些工具、每个什么参数，我们翻译成自己的 Tool 再登记进同一张表。

循环代码不该为它改。如果接一个外部工具要动循环，说明第 2 层的抽象没切对。

## 第 6 层 Skills

搞懂「能力」和「知识」是两回事。工具是能力：模型调用它，我们执行，有结构化的
入参和出参。skill 是知识：一份按需加载的说明书，告诉模型某类任务该怎么做。

差别在占用上下文的方式。工具的定义每次请求都全量带着；skill 平时只露名字和
一句话简介，模型决定要用时才把正文加载进来。所以 skill 适合「偶尔需要的大段知识」，
工具适合「每次都可能用到的小而精确的动作」。

## 贯穿全程的两条线

**观测（trace）。** 每一层的判断都要有数可看，不然就是凭感觉。
一次请求花了多久、首 token 延迟多少、读了多少缓存、工具算了什么，都在
`main.py trace` 里。spans 记「怎么走的」，JSONL 记「说了什么」，回放时拼在一起。

**协议差异收口。** 两家协议的字段名只允许出现在 `adapter.py`。
看到 `if provider == ...` 散落到别处，就是这个边界破了。

## 学完的标准

不看代码，能讲清楚这几件事：

- 一次请求的生命周期：什么时候开始计费、缓存在哪个环节生效、结束原因有哪几种。
- 工具循环为什么是循环：结果交回去之后模型还能再要工具。
- 一个会话的历史存在哪、为什么存在那、崩溃了会丢什么。
- 出了问题先看 trace 的哪一行。
